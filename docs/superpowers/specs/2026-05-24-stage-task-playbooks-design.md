# Playbooks de Etapa e Tarefas Sugeridas - Design

Data: 2026-05-24
Projeto base: Atomic CRM / Prymeira CRM
Status: aprovado em conversa para virar spec

## Objetivo

Deixar o CRM mais inteligente e mais rapido no uso diario criando playbooks de tarefas por pipeline e etapa.

A promessa desta fase e:

> Cada negocio aberto tem proximas acoes claras, cada etapa ensina o vendedor o que fazer, e cada pipeline pode ter seu proprio jeito de trabalhar.

O foco nao e adicionar IA generativa nesta primeira versao. O foco e transformar o processo comercial em sugestoes operacionais de um clique, configuraveis por pipeline.

## Contexto Atual

O CRM ja tem:

- `pipelines`, com `stages` por pipeline;
- `deals`, com `pipeline_id`, `stage`, `next_action_at` e `last_activity_at`;
- `tasks`, com vinculos opcionais para `contact_id`, `lead_id` e `deal_id`;
- indicadores de risco no card do deal, incluindo "sem proxima acao";
- automacoes comerciais basicas em `automation_rules` e `automation_runs`;
- provider Postgres em `src/components/atomic-crm/providers/postgres/dataProvider.ts`, chamando `/api/records/...`;
- backend Postgres em `server/index.js`, com allowlist de recursos e isolamento por `workspace_id`;
- FakeRest para demo/testes locais.

Importante: a implementacao alvo e Postgres + API propria, nao Supabase client como runtime principal. Arquivos antigos com nome `supabase/` ainda podem existir como historico/conveniencia de SQL, mas a feature deve ser desenhada para o backend Postgres atual.

## Decisoes Aprovadas

1. O comportamento sera hibrido: templates podem ser manuais ou automaticos.
2. A configuracao sera hibrida: tela completa em Configuracoes e atalho discreto no Kanban para editar a etapa atual.
3. Os campos serao progressivos: essenciais visiveis primeiro, avancados recolhidos.
4. A abordagem tecnica sera uma tabela propria de templates por etapa, em vez de guardar tudo no JSON do pipeline ou misturar sugestoes manuais dentro de `automation_rules`.

## Escopo

Esta fase entrega:

- tabela/recurso `stage_task_templates`;
- exibicao de sugestoes no detalhe do negocio;
- criacao manual de tarefa a partir de sugestao;
- criacao automatica de tarefa quando um deal entra numa etapa com template automatico;
- deduplicacao de execucoes automaticas;
- configuracao dos templates por pipeline e etapa;
- atalho de configuracao a partir do Kanban;
- dados demo no FakeRest;
- testes de utilitarios, automacao e componentes principais.

Ficam fora desta fase:

- IA gerando tarefas automaticamente;
- scoring preditivo;
- regras condicionais complexas por valor, segmento, categoria ou responsavel;
- notificacoes externas por email, WhatsApp ou Slack;
- editor visual de workflow;
- obrigatoriedade/bloqueio para mover deal sem tarefa feita.

## Modelo de Dados

Criar `stage_task_templates`.

Campos propostos:

- `id bigint generated by default as identity primary key`;
- `workspace_id uuid not null`;
- `pipeline_id bigint not null references public.pipelines(id) on update cascade on delete cascade`;
- `stage text not null`;
- `name text not null`;
- `task_text text not null`;
- `task_type text not null default 'follow-up'`;
- `due_in_days integer not null default 0`;
- `mode text not null default 'manual'`;
- `enabled boolean not null default true`;
- `instructions text`;
- `assignee text not null default 'record_owner'`;
- `index smallint not null default 0`;
- `created_at timestamp with time zone not null default now()`;
- `updated_at timestamp with time zone not null default now()`;
- check `due_in_days >= 0`;
- check `mode in ('manual', 'automatic')`;
- check `assignee in ('record_owner')` para a primeira versao.

Indices:

- `(workspace_id)`;
- `(workspace_id, pipeline_id, stage, enabled)`;
- `(workspace_id, pipeline_id, stage, index)`.

Para deduplicacao automatica, usar `automation_runs` com um `rule_key` estavel derivado do template, por exemplo:

`stage-task-template.<template_id>.<stage>`

A unicidade atual de `automation_runs` por `(workspace_id, rule_key, trigger_resource, trigger_record_id)` cobre "este template automatico ja rodou para este deal". Se a implementacao precisar permitir rodar novamente quando o deal sair e voltar para a etapa, isso deve ser uma decisao separada. Na primeira versao, nao duplica.

## API Postgres

Registrar `stage_task_templates` em `server/index.js`:

- adicionar em `tenantResources`;
- adicionar em `resources` com leitura e escrita;
- confirmar que `sanitizeWriteData` injeta `workspace_id`;
- confirmar que listagem, criacao, edicao e exclusao funcionam via `/api/records/stage_task_templates`.

Como o endpoint generico filtra colunas reais da tabela, a migracao precisa estar aplicada antes de writes do novo recurso.

Permissoes esperadas:

- usuarios autenticados no workspace podem ler templates;
- admins/power users devem poder criar, editar e excluir templates;
- se o backend ainda nao diferencia write por perfil no endpoint generico, a primeira versao pode seguir o mesmo padrao dos recursos editaveis atuais, mas a UI deve esconder/limitar a tela de configuracao usando `CanAccess` ou regra equivalente.

## Frontend: Uso Diario

No card do Kanban:

- manter os indicadores atuais de valor, probabilidade, valor ponderado e risco;
- adicionar um badge compacto quando houver sugestoes disponiveis para a etapa atual, por exemplo `3 sugestoes`;
- preservar a abertura do detalhe do deal ao clicar no card.

No modal/detalhe do deal:

- adicionar um painel compacto `Proximas acoes sugeridas`;
- listar templates ativos da combinacao `pipeline_id + stage`;
- separar visualmente sugestoes manuais e automaticas ja criadas, se isso ajudar a leitura;
- botao de um clique cria tarefa real;
- mostrar tarefas abertas do deal logo abaixo ou no mesmo painel;
- destacar tarefas atrasadas usando a logica/listas existentes de `tasks`.

Criacao manual a partir de sugestao:

1. Usuario abre deal.
2. Clica em uma sugestao.
3. CRM cria `tasks` com:
   - `deal_id` do negocio;
   - `contact_id` principal quando houver um contato claro;
   - `type` do template;
   - `text` renderizado a partir de variaveis simples;
   - `due_date` = agora + `due_in_days`;
   - `sales_id` = dono do deal ou usuario atual, seguindo o padrao existente;
   - `automation_run_id` nulo para criacao manual.
4. CRM atualiza `deals.next_action_at` quando a nova tarefa for a proxima acao mais relevante.
5. Painel refaz a consulta e mostra a tarefa criada.

Variaveis de texto iniciais:

- `{{deal.name}}`;
- `{{company.name}}`, quando houver empresa;
- `{{contact.name}}`, quando houver contato principal.

Se uma variavel nao existir, renderizar string vazia ou remover espacos duplicados. Nao bloquear a criacao por falta de variavel opcional.

## Frontend: Configuracao

Tela completa em Configuracoes:

- listar pipelines;
- ao selecionar pipeline, listar etapas;
- ao selecionar etapa, listar templates em ordem;
- permitir adicionar, editar, reordenar, ativar/desativar e excluir templates;
- mostrar campos essenciais primeiro:
  - nome;
  - texto da tarefa;
  - tipo;
  - prazo em dias;
  - modo manual/automatico.
- mostrar campos avancados recolhidos:
  - instrucoes;
  - ordem;
  - ativo/inativo;
  - responsavel.

Atalho no Kanban:

- cada coluna pode ter uma acao discreta `Editar playbook da etapa`;
- o atalho abre a configuracao ja filtrada para o pipeline e etapa atuais;
- se a UI do Kanban ficar carregada, o atalho deve ficar em menu/icone, nao como botao grande permanente.

Protecoes:

- se uma etapa tiver templates e o usuario tentar remover/renomear a etapa, avisar que ha playbooks vinculados;
- se um pipeline for excluido, templates sao excluidos por cascade;
- se nao houver templates numa etapa, o painel do deal pode mostrar estado vazio pequeno com atalho de configuracao para admin.

## Automacao

Estender o motor comum em `src/components/atomic-crm/providers/commons/automationEngine.ts`.

Comportamento:

1. Em update de deal, detectar mudanca de `stage` ou entrada em uma etapa.
2. Buscar templates automaticos ativos por `pipeline_id + stage`.
3. Para cada template, tentar registrar uma execucao em `automation_runs`.
4. Se a execucao ja existir, nao criar tarefa.
5. Se nao existir, criar task vinculada ao deal e atualizar a execucao com `action_resource = 'tasks'` e `action_record_id`.

O motor deve continuar funcionando tanto no provider Postgres quanto no FakeRest.

O `rule_key` deve ser deterministico e estavel. Renomear template nao deve alterar `rule_key`; usar `id` e etapa e suficiente para a primeira versao.

## Riscos e Decisoes em Aberto

- O repositorio ainda contem caminhos e docs com nome Supabase. A implementacao deve seguir o backend Postgres atual e so tocar SQL/migracoes antigas se elas ainda forem a fonte real do schema.
- O endpoint generico em `server/index.js` talvez precise de regras de acesso mais finas para impedir que usuarios nao-admin editem playbooks. Se isso nao existir hoje, tratar como melhoria de seguranca dentro da implementacao ou abrir uma tarefa separada.
- Contato principal de um deal ainda e um array `contact_ids`. A primeira versao pode escolher o primeiro contato como principal para a task, mas isso deve ficar explicito no codigo.
- Reabrir um deal numa etapa com template automatico nao deve duplicar tarefa na primeira versao. Se o processo comercial pedir recorrencia, isso vira configuracao posterior.

## Resultado Esperado

Depois da entrega:

- deals sem proxima acao ficam mais faceis de corrigir;
- vendedores criam follow-ups com um clique;
- admins configuram o processo por pipeline e etapa;
- pipelines de pos-venda ou renovacao conseguem ter playbooks proprios;
- o CRM fica mais inteligente por processo antes de depender de IA.
